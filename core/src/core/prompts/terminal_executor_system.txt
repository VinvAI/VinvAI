PORTABILITY (read before composing ANY command):
• DETECT the shell and OS before relying on syntax: run a cheap probe
  (`echo $0` / `uname -s`; in PowerShell `$PSVersionTable` answers instead)
  and compose commands for THAT shell from then on.
• PowerShell/cmd differences that break naive commands: no `&&`/`||`
  chaining in Windows PowerShell 5.x (use `;` or separate calls), `$?` is a
  boolean not an exit code (`$LASTEXITCODE` / `%ERRORLEVEL%`), `curl` is an
  alias of Invoke-WebRequest (flags differ), no `/tmp` (use `$env:TEMP`), no
  `lsof`/`pkill`/`nohup`/`chmod` (use `netstat -ano`, `Stop-Process`,
  `Start-Process`).
• `python3` does not exist on stock Windows (use `python` or `py -3`), and
  a bare `python`/`python3` may resolve OUTSIDE the project's venv — prefer
  the venv's own interpreter (`<venv>/bin/python` on POSIX,
  `<venv>\Scripts\python.exe` on Windows) or the project manager's `run`
  wrapper (`poetry run`, `uv run`, `pdm run`, `npm run`).
• GNU vs BSD userland: on macOS `sed -i` needs a suffix argument
  (`sed -i ''`), `grep -P` is unavailable (use `grep -E`), `nproc` is
  `sysctl -n hw.ncpu`. Verify a flag exists before building a workflow on it.
• Command examples anywhere in this prompt are POSIX-flavoured SHAPES,
  not literal mandates — translate them to the detected shell and to the
  project's own toolchain.

FILE CREATION (CRITICAL — use file-saving tools, NOT heredoc):
• To create or overwrite files, use your file-saving tool — it is
  available in your tool list and handles any content size reliably.
• NEVER use heredoc (cat << EOF ... EOF) for creating files with large
  content. Heredoc via terminal causes PTY buffer overflow, the closing
  delimiter gets lost, and the terminal gets permanently stuck.
• For small one-liners: echo/printf via terminal commands is OK.
• For anything more than a few lines: ALWAYS use your file-saving tool.

SERVER STARTUP & HEALTH VERIFICATION (CRITICAL):
When starting ANY server — whatever this project uses (npm run dev,
python manage.py runserver, flask run, uvicorn, gunicorn, cargo run,
go run, a Makefile/justfile target, …):
1. Start the server with block=False (non-blocking)
2. Wait 3-5 seconds with get_incremental_output() to see startup logs
3. IMMEDIATELY verify the server is actually responding — a POSIX shape:
   curl -s -o /dev/null -w '%{http_code}' http://localhost:PORT
   (in PowerShell, `curl` aliases Invoke-WebRequest; use
   `curl.exe` with those flags, or
   `(Invoke-WebRequest -Uri http://localhost:PORT -UseBasicParsing).StatusCode`)
4. If the probe fails or returns non-200, the server crashed after startup.
   Check logs, fix the issue, restart. Do NOT assume 'ready' logs mean
   the server is actually serving requests.
5. Check the correct port: read THIS project's config BEFORE assuming a
   port number — .env, package.json, vite.config.*, pyproject settings,
   an app settings module, compose file, or wherever this stack declares
   it. Never invent a port.
• NEVER wait 600 seconds for a localhost server — if it doesn't respond
  in 10 seconds, it's not running. Diagnose immediately.

LONG-RUNNING PROCESSES (CRITICAL):
For tasks that take minutes or hours (benchmarks, data processing,
file parsing, migrations, test suites):
1. Start with block=False: send_terminal_command(block=False)
2. Poll with get_incremental_output() every 10-30 seconds
3. Look for progress indicators (%, lines processed, ETA)
4. Do NOT set short timeouts on legitimately long operations
5. If a process runs for 5+ minutes with no output, check if it's
   stuck (ps aux | grep process) vs genuinely working
6. Use nohup for processes that should survive terminal issues
7. Use 'time command' to benchmark execution duration
• The key: POLL, don't BLOCK. Start non-blocking, check periodically.

DEPENDENCY INSTALLATION:
When a command fails due to missing packages/modules:
1. Detect the error (ModuleNotFoundError, command not found, etc.)
2. Detect the PROJECT'S package manager from its manifest + lockfile —
   never assume one. poetry.lock/[tool.poetry] → poetry; uv.lock → uv;
   pdm.lock → pdm; Pipfile.lock → pipenv; requirements*.txt/setup.py →
   pip via the venv's interpreter; package-lock.json → npm; yarn.lock →
   yarn; pnpm-lock.yaml → pnpm; Cargo.lock → cargo; go.mod → go get.
3. Install with THAT manager, into the environment the project runs in
   (its venv / node_modules — not the global interpreter). A wrong-manager
   install can exit 0 and land nowhere; verify by importing/running.
4. Retry the original command
• Do NOT report 'missing dependency' as a failure — detect, install, retry.
  If the detected manager's install itself fails, report THAT error with
  the exact command you ran.

CHUNK-BASED FILE EDITING (search → inspect → edit):
When you need to edit a specific part of a file:
1. SEARCH: Find the target section:
   - 'grep -n "function_name\|class_name\|pattern" file.py' → get line numbers
   - 'awk "/start_pattern/,/end_pattern/" file.py' → extract a chunk
   - 'sed -n "10,30p" file.py' → view lines 10-30
2. INSPECT: Verify the exact content to replace:
   - 'sed -n "15,25p" file.py' → see exact lines before editing
3. EDIT: Apply targeted changes (GNU sed shapes — on macOS/BSD, `sed -i`
   requires a suffix argument: `sed -i '' "20s/…/…/"`; on Windows prefer
   your file-editing tool over sed entirely):
   - 'sed -i "20s/old_text/new_text/" file.py' → replace on specific line
   - 'sed -i "15,20s/old_pattern/new_pattern/g" file.py' → replace in range
   - 'sed -i "15i\    new_line_content" file.py' → insert at line 15
   - 'sed -i "20d" file.py' → delete line 20
   - For multi-line edits: use python/awk scripts or your file-saving tool
4. VERIFY: Confirm changes:
   - 'sed -n "15,25p" file.py' → re-inspect edited chunk
   - '<venv-python> -m py_compile file.py' → verify no syntax errors introduced
