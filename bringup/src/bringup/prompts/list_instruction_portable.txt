## Vinv bring-up — Python service inventory (read-only, portable runbook)

You are producing a machine-readable inventory of the **Python services** in this repo. This
stage installs nothing and starts nothing — it only reads and describes. Use your own terminal
and file-editing tools; this runbook names no specific tool APIs.

### What counts as a "service"

A service is a Python distribution/component we instrument — the unit a later
`bringup start --service <name>` brings up while tracelens AST-rewrites its import package(s).
Most repos ship one per packaging manifest (`pyproject.toml` / `setup.py`); the framework scan
below lists the candidates it found and, for each, the import package(s) that belong in `modules`.
EXCLUDE stateful infrastructure (Postgres, MySQL, Redis, ClickHouse, Kafka, Mongo, etc.) and
non-Python processes (Node/Vite/Next frontends). Only Python services count.

**"Service" is broader than HTTP.** Include every long-running Python process the repo defines:
web apps (`python_web`), background/queue workers (`python_worker`), **stdio JSON-RPC servers**
(`python_stdio` — MCP servers and the like, spoken to over stdin/stdout, no port), and beat/cron
schedulers (`python_scheduler`). A port scan finds none of the last three — find them from the
handbook's enumeration, the manifest-scan list below, and the entry code.

**"Service" is also broader than long-running.** Tracelens instruments a *process*, not a server:
`tracelens run -t pkg -- <any command>` records a run that starts, works and exits just as
faithfully as one that stays up. So the inventory also covers `python_cli` (a console script or
`__main__` invoked with argv and run to completion) and `python_library` (an importable package
with no entrypoint of its own, whose functions the exerciser calls). In a toolchain, a SDK or a
framework these are the *only* units of work there are — omit them and the repo traces nothing.
The discriminator is whether the entrypoint **blocks**, never whether it declares a console
script: read the target function and see whether it parks on a serve loop or returns.

**NEVER FABRICATE A `command`.** A package with no runnable process of its own — no
`[project.scripts]` / `[tool.poetry.scripts]` console script, no `__main__.py`, no handbook
`### Run on host` row — is a library, and inventing an entrypoint for it burns a whole downstream
bring-up attempt. Three legitimate outcomes: if another service's process imports and runs its
code, list it with **that host app's** command/working directory/port (entries then differ only in
which package is instrumented); if nothing runs it but its functions can be called, list it as
`kind: "python_library"` and **omit `command`** so the harness can synthesize the exerciser
function driver (the normal outcome); leave it out entirely only when nothing should ever call it
(a vendored copy, a dev-only shim, generated code).

### What to capture for each service

- **`name`** — the service name: the candidate name from the scan verbatim; for a service you add
  from the handbook, its distribution name (its `pyproject.toml` `[project].name` or
  `[tool.poetry].name`, whichever table the manifest uses).
- **`kind`** — `python_web` (serves HTTP), `python_worker` (background worker/consumer, no HTTP
  port), `python_stdio` (stdio JSON-RPC server — MCP style, port-less, requests on stdin /
  responses on stdout), `python_scheduler` (beat/cron-style scheduler process), `python_cli` (runs
  to completion and exits), or `python_library` (no entrypoint of its own). Classify by **reading
  the entry code** the command names: `uvicorn.run`/an ASGI app → `python_web`; a `FastMCP(...)`
  app or `mcp` stdio transport → `python_stdio`; a celery worker → `python_worker`; a
  beat/scheduler loop → `python_scheduler`; a target that computes something, prints it and
  **returns** → `python_cli`. Verify every candidate is actually startable this way before
  emitting it — a candidate whose entry code you could not locate does not go in the file.
- **`transport`** — optional: `"http"` for `python_web`, `"stdio"` for `python_stdio`, else
  omit/`null`. A `python_stdio` service's readiness check downstream is a JSON-RPC initialize
  round-trip over stdin/stdout (recorded by Stage 2b as `"probe": {{"type": "stdio-jsonrpc"}}` in
  start_commands), never a port probe. `python_cli` / `python_library` are never spoken to over a
  transport — omit it; their downstream check is `"probe": {{"type": "exit"}}`, the process
  running to completion with the expected exit code and a non-empty trace.
- **`invocations`** — optional, and only for `python_cli` / `python_library`: the representative
  ways this unit is driven, each a **complete runnable command** (not an argv fragment) with a
  short stable **`id`** (`report`, `check`), an optional `purpose` and an `expect_exit` that
  defaults to `0`. The id is the unit identity downstream — findings and coverage key on
  `<service>#<id>` — so give every entry one. Ground the subcommand and its argv in what the repo
  declares — the CLI's own `--help`/command definitions, a README example, a CI step, a Makefile
  target. Omit the field and `command` becomes the single invocation.
- **`params`** — optional, per invocation: the arguments a human should be able to change at run
  time. Write the command as a template with `{{name}}` placeholders and declare one entry per
  placeholder — `{{"name": "since", "type": "string", "default": "7d", "help": "lookback window"}}`.
  `type` is one of `string` (default), `int`, `float`, `enum` (needs `choices`), `path`, `flag`.
  **The `default` is what actually runs** in every headless pass, so rendering the template with
  the defaults must reproduce exactly the command you verified. Ground defaults and choices in the
  CLI's own `--help` / `@click.option` / `argparse` definitions — never invent one. Parameterize
  only what a person genuinely retypes (a path, a date range, an output format), not every flag.
- **`command`** — the native start command (NEVER `docker compose up`), taken from what the repo
  **actually declares**: the handbook's `### Run on host` row, a `[project.scripts]` /
  `[tool.poetry.scripts]` console script, a verified `python -m <module>` target (only if that
  package really has a `__main__.py` — check), or the server command the project documents
  (uvicorn/gunicorn/`manage.py runserver`/`flask run`/…, in `python -m <server> …` form where
  supported). A command you could not ground in the handbook, a manifest script, or an existing
  entrypoint file is a fabrication. **`python -m <module>:<attr>` is INVALID** — `-m` takes a
  module, not an app-factory reference. Services served by the same app process may share a
  `command`. For `python_library`, **omit `command`** entirely.
- **`working_directory`** — absolute path the command runs from (default the candidate's own path
  from the scan, else `{root}`).
- **`port`** — the HTTP port it listens on (**required** for `python_web`); `null` for every
  other kind (`python_stdio` / `python_cli` / `python_library` in particular MUST have
  `port: null` — they never listen).
- **`modules`** — the top-level **import package(s)** to instrument; each must be a valid Python
  identifier (never a directory or distribution name containing `-`).

### Write the file

Write this JSON to `{services_json}` with your file-writing tool — one entry per Python service,
no infra, no frontends:

```json
{{
  "services": [
    {{
      "name": "acme-payment",
      "kind": "python_web",
      "command": "python -m uvicorn acme_payment.main:app --host 0.0.0.0 --port 8000",
      "working_directory": "{root}",
      "port": 8000,
      "modules": ["acme_payment"]
    }},
    {{
      "name": "toolshed",
      "kind": "python_worker",
      "command": "python -m toolshed",
      "working_directory": "{root}",
      "port": null,
      "modules": ["toolshed"]
    }},
    {{
      "name": "acme-mcp",
      "kind": "python_stdio",
      "transport": "stdio",
      "command": "python -m acme_mcp.server",
      "working_directory": "{root}",
      "port": null,
      "modules": ["acme_mcp"]
    }},
    {{
      "name": "acme-tool",
      "kind": "python_cli",
      "command": "acme-tool report --since 7d",
      "working_directory": "{root}",
      "port": null,
      "modules": ["acme_tool"],
      "invocations": [
        {{"id": "report", "command": "acme-tool report --since {{since}}",
          "purpose": "the reporting path",
          "params": [{{"name": "since", "default": "7d", "help": "lookback window"}}]}},
        {{"id": "check", "command": "acme-tool check ./sample",
          "purpose": "the validation path", "expect_exit": 1}}
      ]
    }},
    {{
      "name": "acme-sdk",
      "kind": "python_library",
      "working_directory": "{root}",
      "port": null,
      "modules": ["acme_sdk"]
    }}
  ]
}}
```

(The names above are illustrative of the **shape** — note how the service `name` may carry a dash
while `modules` carries the underscore import package, how the stdio server carries
`transport: "stdio"` with `port: null`, how the CLI's `invocations` are each a full command with
its own stable `id`, how the first carries a `{{since}}` slot a human can change while the second
documents a legitimate non-zero exit, and how the library entry carries **no `command` at all**.
Use the actual names for this repo.) Emit
**valid JSON only** (no trailing commas, no comments, no Markdown fences inside the file).

### Finish

You are done only when **`{services_json}` exists on disk** with a valid `services` array covering
every service in the handbook. Reading and thinking are not a substitute for writing the file.
Validation to expect: every `modules` entry must be an importable Python identifier, `kind` must
be one of `python_web` / `python_worker` / `python_stdio` / `python_scheduler` / `python_cli` /
`python_library`, `python_web` entries must carry an integer `port`, `python_stdio` / `python_cli`
/ `python_library` entries must carry `port: null`, `transport` (when present) must match the
kind, `invocations` (when present) may only appear on `python_cli` / `python_library` and each
entry must carry a full `command` and a unique `id`, every `params` entry must name a
`{{placeholder}}` the command actually contains (and vice versa) and render with its defaults,
every entry except `python_library` must carry a `command`, and commands must be runnable (no
`-m module:attr`, no docker).
