## Vinv bring-up — start one service (portable runbook)

You are bringing up **one** service, **`{service}`**, in this repo and **only** that service —
wrapping it with `tracelens run` if it is a Python process so we can capture traces for downstream
RCA. Use your own terminal and file-editing tools; this runbook names no specific tool APIs, so map
each step onto whatever terminal / file primitives you have.

### Prime directive — GET THE SERVICE RUNNING

Get **`{service}`** actually serving traffic. Diagnose and fix errors; do **not** bail on the first
failure. Common self-heals:

- `No module named pip` → the venv was made by a tool that doesn't install pip into it; use **that
  project's own installer** (detect it — see below), not a guessed one.
- `command not found: python` → use **`python3`** or the venv's interpreter (`<venv>/bin/python`, or
  `<venv>\Scripts\python.exe` on Windows).
- missing venv / deps → create it **with the project's own toolchain** and install (see below).
- port already in use → **never a reason to stop, and never `verified:false`.** Find the holder
  (`lsof -nP -iTCP:<port> -sTCP:LISTEN`, or `netstat -ano | findstr :<port>` on Windows), then take
  exactly one of two remedies. **The holder is this service** (its command line names this repo, its
  venv, `tracelens`, or the module you are starting) → kill it and reuse the port: `kill -9 <pid>`,
  or `taskkill //F //T //PID <pid>` from Git Bash on Windows (`taskkill /F /T /PID <pid>` from
  PowerShell — MSYS rewrites a lone `/F` into a path); re-probe and require the port free before
  launching. **The holder is something else** (another app, a container, a system service) → leave it
  alone and MOVE this service to a free port: pass it explicitly (`--port <free>` or the app's own env
  var) and use that same port everywhere afterwards — the readiness probe, the `verification.port` you
  record, and the recorded command string. Never drop the port flag to dodge the conflict, and never
  kill a process you cannot identify.
- import/version conflict → prefer the project's **lockfile** resolution; hand-pin only if the lock
  cannot be honoured, then retry.
- a genuinely **unreachable** infra dependency (DB/broker: connection refused / DNS failure) → start
  it and retry. A dependency that is merely **slow** (a pool taking 20–40s) is NOT a failure.

### Source of truth

Read the handbook at `{vinv_md}` first (also inlined above this runbook if present). Find how
**`{service}`** is run — the `### Run on host (instrumented by tracelens)` table, the package's own
`__main__.py` / entrypoint, and `pyproject.toml` scripts. Treat it as authoritative for **what** to
install and **what** to start.

### CRITICAL — Python apps run on the HOST, never in Docker

Tracelens instruments Python by AST-rewriting modules at import time inside the **host** interpreter
that `tracelens run` launches. If the app runs inside a Docker container, the wrapper sits outside
the container and never wraps the real `python` process — **zero spans land** and downstream RCA has
nothing. So: start only **stateful infrastructure** (Postgres/Redis/Kafka/…) in Docker
(`docker compose up -d <infra-svc> …`, NOT the whole stack), and run the Python app itself
**natively on the host**, pointed at the dockerised infra's loopback ports. If the handbook only
documents `docker compose up`, derive the native command from the container's `CMD` / `ENTRYPOINT`.

### STEP 0 — Detect the package manager. NEVER assume one.

**Before installing anything, determine which manager THIS repo uses.** Each manager reads only its
own manifest format and is blind to the others'. Detect from the manifest + lockfile:

| Evidence                                        | Manager | Install                 | Run                |
| :---------------------------------------------- | :------ | :---------------------- | :----------------- |
| `[tool.poetry]` in pyproject / `poetry.lock`     | Poetry  | `poetry install`        | `poetry run <cmd>` |
| `[project]` in pyproject + `uv.lock`             | uv      | `uv sync`               | `uv run <cmd>`     |
| `[tool.pdm]` / `pdm.lock`                        | PDM     | `pdm install`           | `pdm run <cmd>`    |
| `Pipfile.lock`                                   | Pipenv  | `pipenv install`        | `pipenv run <cmd>` |
| `requirements*.txt`, `setup.py`, or `[project]` with no lock | pip | `pip install -r <f>` / `-e .` | `<venv>/bin/python -m …` |
| `environment.yml`                                | conda   | `conda env create -f …` | `conda run -n <env> <cmd>` |

Non-Python: `package-lock.json` → `npm ci`; `yarn.lock` → `yarn install`; `pnpm-lock.yaml` →
`pnpm i --frozen-lockfile`; `bun.lockb` → `bun install`; `Cargo.lock` → `cargo build`.

**The manifest table wins over a stray lockfile's name** (a `uv.lock` may be debris from an earlier
failed attempt — possibly your own). **The handbook wins over both**: if `{vinv_md}` documents an
install command, run THAT verbatim. In a monorepo, detect **per directory**.

**THE TRAP — the wrong manager EXITS 0 AND INSTALLS NOTHING.** No error, a valid near-empty stub
lockfile, a correctly-created but **empty** venv, and a `ModuleNotFoundError` much later at import
time. A manager that reads `[project]` sees a `[tool.poetry]`-only manifest as having zero
dependencies and faithfully installs zero. **So when deps are missing after a "successful" install,
your first hypothesis is "wrong installer", NOT "wrong venv".** Do not create a second venv — that
splits the app's deps from the instrumentation and neither venv can then run a traced service.

**Verification gate (mandatory):** exit code 0 is not proof. Import a real dep before continuing:
`<venv-python> -c "import fastapi, uvicorn; print('deps OK')"` (use this service's actual deps). If
it raises `ModuleNotFoundError`, the install failed regardless of exit code — switch managers and
retry into the SAME venv. Do not proceed to OTel or start the service until it prints.

### Virtualenv — pin Python 3.13 (or 3.12)

When you create a fresh venv, pin it to 3.13 (or 3.12) unless the manifest requires newer, and
create it **with the project's own toolchain** (`poetry env use 3.13`, `uv venv --python 3.13`,
`pdm use 3.13`, `python3.13 -m venv .venv`) so manager and venv agree. Given no explicit version,
most tools pick the newest interpreter installed (often 3.14), for which many C-extension wheels
don't exist yet on PyPI — forcing 5–15+ min source builds that burn your budget.

### Start the service under tracelens

1. **Target packages are pre-computed — do not guess.** {_target_pkg_note}

   **The deliverable is that THIS SERVICE'S OWN CODE gets traced.** These flags are
   the framework's best answer, not a ceiling. Check that the module your entrypoint
   lives in is covered: for `-m uvicorn pkg.sub.app:app` that is `pkg`, for
   `python dir/thing.py` it is `dir`. If it is not covered, **add a
   `--target-package` for it** — a directory without `__init__.py` is a valid target
   (tracelens treats it as a source root). A service that starts green while its own
   handlers emit no spans is a FAILED bring-up.

   **If you add a target the flags above did not list, you MUST record which one in
   the deliverable** (`added_target_packages`, see below). Without it the recorded
   file is indistinguishable from one where the framework supplied every flag, so
   nobody can tell whether the engine's target derivation works or an agent has been
   quietly compensating for it.
2. **Convert the launch command to Python-script form** so tracelens's `runpy` dispatch keeps the
   AST hook installed: replace `uvicorn ARGS` with `python -m uvicorn ARGS`, and drop `--reload`
   (reload forks workers and loses child-process spans).
3. **Compose the wrapped command** with the exact `--target-package` flags below:

   ```bash
   PATH="{_venv_bin}:$PATH" {_tracelens_cmd} run \
{_target_pkg_flags}     --output {_caps_base}/{tracelens_subdir}<service-name>/trace.jsonl \
     --sample-rate 1.0 \
     -- {_venv_python} -m <module> <original-args>
   ```

   {_tracelens_path_note}

   Start the service in exactly this venv-qualified form — it is the same string
   you will record as the deliverable. Starting it some other way (an activated
   venv, a bare `tracelens`) means the string you verified is not the string you
   record, and the recorded one has never been run.

   The output path **must** include the `{_g0}` segment shown above — skipping it mingles traces
   with prior projects' baselines and downstream identification misattributes spans.
4. **Start the server as a long-running background process in its own terminal** — never as a
   blocking/foreground call with a timeout. A tracelens-wrapped server never returns to the prompt;
   a timeout would send SIGINT and kill it mid-startup (exit 130) before it finishes booting.
5. **Poll for the app's OWN readiness marker, patiently.** Readiness is the server's startup-complete
   log line (`Application startup complete` / `Uvicorn running on`), NOT an HTTP probe. Real apps
   (uvicorn with DB pools, migrations, model loads) take **30–90s**, heavy ones **2–4 min**, to
   finish startup. Until then the socket may be bound (so `lsof` shows LISTEN) but every request
   returns an empty reply / HTTP `000` — that combination means **still booting**, not failed.
   - **Two positive proofs it is alive and you must keep waiting:** the `trace.jsonl` line count is
     **growing** (`wc -l {_caps_base}/{_g0}<service>/trace.jsonl` a few seconds apart), or the
     process is in the table (`pgrep -af "tracelens run|<module>"`, or `tasklist | grep -i tracelens`
     on Windows).
   - **Use the port-probe tool this host actually has** — `lsof` on macOS/Linux, `netstat -ano |
     grep -w LISTENING | grep ':<port>'` on Windows. `lsof: command not found` in Git Bash says
     nothing about the server; it is not a "not listening" result.
   - Ignore benign `Attempting to instrument while already instrumented` noise — it is not a crash.
   - **Do NOT relaunch a server that is still booting** — each relaunch resets the startup clock and
     throws away all boot progress. As long as the log keeps advancing, keep waiting.
   - Read the server's log **read-only**; run every `sleep` / `lsof` / `curl` / `wc -l` in a
     **different** terminal so you never type into the running server and shut it down.
   - Conclude failure only after a real **traceback**, the **process exiting**, or the log going
     **completely silent** for ~30s+ while the trace count is flat.
6. **Confirm it serves a real request.** Once startup is complete and the port is LISTENing, `curl`
   a real endpoint (`/health`, `/docs`, `/`). A 2xx/3xx/401 **plus** a non-zero `trace.jsonl` line
   count = **verified**. A 500 on every request means it booted but isn't really serving — check
   tracelens flags / env / instrumentation conflicts.
7. **Stop the service, then record the command.** The deliverable is the *verified start command*,
   not a live process. Find the listening PID with whichever tool this host has — `lsof -nP
   -iTCP:<port> -sTCP:LISTEN` on macOS/Linux, or `netstat -ano | grep -w LISTENING | grep ':<port>'`
   on Windows, where the PID is the LAST column (Git Bash has no `lsof`; its "command not found" is
   not evidence the service stopped). Then stop it:
   - **macOS/Linux:** `kill -TERM <pid>` — tracelens flushes its JSONL and writes
     `<output>.summary.json` on the way out.
   - **Windows:** `kill -TERM` **does not work and lies about it** — MSYS `kill` knows only MSYS
     pids, so against a native pid it answers `No such process` and exits 1 **while the server is
     still serving**. Never read that as "already stopped". Use taskkill on **the PID the probe just
     gave you**: `taskkill //F //T //PID <pid>` from Git Bash, or `taskkill /F /T /PID <pid>` from
     PowerShell/cmd. **The doubled slashes are required in Git Bash and are not a typo** — MSYS
     rewrites a lone `/F` into the path `F:/` before taskkill sees it, so the single-slash form dies
     with `ERROR: Invalid argument/option - 'F:/'` and leaves the port held. No tree-walking is
     needed: `/T` takes the children, and the `tracelens.exe → python.exe → python.exe` parents
     above the listener exit on their own once it dies. Plain `taskkill` without `/F` is refused
     here, so `//F //T` is the expected form.

   **Confirm the port is actually free before finishing** — re-run the probe and require it to
   return nothing. A bring-up that leaves the port held makes the NEXT launch die with "address
   already in use". On Windows the forced kill skips tracelens's shutdown hook so
   `<output>.summary.json` is not written; that is an accepted loss (`trace.jsonl` is what
   downstream needs) — do not retry over it and do not call the verification failed.

### REQUIRED DELIVERABLE — write the verified start command(s)

After the service is confirmed alive (port LISTENing + serves a request, and for a Python service
`trace.jsonl` has non-zero lines), write this JSON to `{start_commands_json}` with your file-writing
tool:

```json
{{
  "service": "{service}",
  "verified": true,
  "added_target_packages": [],
  "verification": {{
    "port": <port-or-null>,
    "listening": true,
    "http_status": <code-or-null>,
    "endpoint_checked": "http://localhost:<port>/health",
    "trace_jsonl": "<path-or-null>",
    "trace_lines": <int-or-null>,
    "probe": {{"type": "port"}}
  }},
  "commands": [
    {{
      "purpose": "start {service} under tracelens",
      "command": "PATH=\"{_venv_bin}:$PATH\" {_tracelens_cmd} run --target-package <pkg> --output {_caps_base}/{_g0}{service}/trace.jsonl --sample-rate 1.0 -- {_venv_python} -m <module> <args>",
      "working_directory": "{_root_json}",
      "session_name": "vinv_{service}"
    }}
  ]
}}
```

**`verification.probe` selects the readiness oracle replayers use** — and you must **classify by
what the process BINDS, not by what it is CALLED.** A service named `*-mcp-server` is very often an
ordinary HTTP app (e.g. a Starlette/FastAPI server that is itself an MCP *client* of some remote
endpoint). Recording `stdio-jsonrpc` for it sets `"port": null`, so **every future replay fails
forever** and no fix episode can repair it — this file lives outside the repo. `services.json`
records `transport` and `port` per service; trust those and your own curl over the name. If you
verified it by hitting a port, it is a **port** probe whatever it is called.

Record the one matching what the service actually is: `{{"type": "port"}}` for an HTTP service
(default when `port` is set); `{{"type": "stdio-jsonrpc"}}` ONLY for a server that genuinely binds
no port and speaks JSON-RPC on stdin/stdout (readiness is
writing one JSON-RPC initialize line to its stdin and getting a JSON line back on stdout; verify
it that way yourself, set port/http_status/endpoint_checked to null, and optionally put the exact
initialize object in `"request"`); `{{"type": "process"}}` for a portless worker/scheduler whose
only oracle is staying alive past the grace window (an entry that exits immediately FAILS it even
with exit code 0); `{{"type": "exit"}}` for a **run-to-completion** unit (`kind: python_cli` or
`python_library` in `.vinv/services.json`) — the exact inverse of `process`, where the process
**exiting is the success**. It passes when the command returns the expected code (`0`, or the
documented non-zero one recorded as `"expect_exit": <code>` inside the probe) AND the trace it
wrote is non-empty; staying alive past the deadline FAILS, because a CLI that never returns is
hung or waiting on stdin. Set port/http_status/endpoint_checked to null.

**For a run-to-completion unit, skip the whole server protocol above.** Run **every** invocation
`.vinv/services.json` records — not just the first — each wrapped in `tracelens run` in the
FOREGROUND, let it finish, then check three things per invocation: the exit code matches that
invocation's own `expect_exit`, the trace file is non-empty (`wc -l < <trace.jsonl>` > 0), and the
output looks like the work happened rather than a usage error. There is no port to probe, no
readiness window, no process to kill and no port to free afterwards. An empty trace after a clean
exit is the failure that matters: it almost always means `--target-package` named a distribution
(`acme-tool`) instead of an import package (`acme_tool`). For `python_library` the invocation is the
exerciser's function driver (`vinv-exerciser functions <repo> --service <name> {{only}}`) under the
same tracelens wrap — the library's own package is what `--target-package` names, never the
exerciser's; leave the `{{only}}` slot empty (it drives every exported callable) and declare it as a
parameter so a human can run one entry point later.

**Then record them ALL in an `invocations` array beside `commands`.** `commands` is a SEQUENCE (a
dependency, then the unit) that every replayer joins with `&&` — recording five subcommands there
would run all five, every time. Alternatives go in `invocations`, one entry per way you verified:

```json
{{
  "service": "{service}",
  "verified": true,
  "verification": {{"port": null, "probe": {{"type": "exit"}}}},
  "commands": [
    {{
      "purpose": "run {service}",
      "command": "PATH=\"{_venv_bin}:$PATH\" {_tracelens_cmd} run --target-package <pkg> --output {_caps_base}/{_g0}{service}/report.trace.jsonl --sample-rate 1.0 -- {_venv_python} -m <module> report --since 7d",
      "working_directory": "{_root_json}"
    }}
  ],
  "invocations": [
    {{
      "id": "report",
      "purpose": "the reporting path",
      "default": true,
      "expect_exit": 0,
      "command": "PATH=\"{_venv_bin}:$PATH\" {_tracelens_cmd} run --target-package <pkg> --output {_caps_base}/{_g0}{service}/report.trace.jsonl --sample-rate 1.0 -- {_venv_python} -m <module> report --since {{since}}",
      "params": [{{"name": "since", "type": "string", "default": "7d", "help": "lookback window"}}],
      "working_directory": "{_root_json}",
      "verification": {{
        "exit_code": 0,
        "trace_jsonl": "{_caps_base}/{_g0}{service}/report.trace.jsonl",
        "trace_lines": <int>,
        "rendered_command": "<the EXACT string you ran — the line above with 7d in the slot>"
      }}
    }},
    {{
      "id": "check",
      "purpose": "the validation path",
      "expect_exit": 1,
      "command": "PATH=\"{_venv_bin}:$PATH\" {_tracelens_cmd} run --target-package <pkg> --output {_caps_base}/{_g0}{service}/check.trace.jsonl --sample-rate 1.0 -- {_venv_python} -m <module> check ./sample",
      "working_directory": "{_root_json}",
      "verification": {{
        "exit_code": 1,
        "trace_jsonl": "{_caps_base}/{_g0}{service}/check.trace.jsonl",
        "trace_lines": <int>
      }}
    }}
  ]
}}
```

- **Every entry must have RUN AND PASSED** — the harness replays all of them and the file fails if
  any does. A CLI with four subcommands whose file records one has three nobody can run.
- **`id` is the unit identity downstream** (findings and coverage key on `<service>#<id>`): short,
  stable, from the subcommand — never positional.
- **`expect_exit` is per invocation**; a `check` that exits 1 on findings is working.
- **Each needs its OWN `--output` path**, or the last run overwrites the rest.
- **`default: true`** marks the one the ▶ button, the probe pass and the replay gate run with no
  questions asked — the cheapest representative run, never a destructive one. `commands` keeps
  holding that same string so anything reading only that field still works.
- **`params` are optional and must round-trip:** template the command with `{{name}}` slots, put the
  value you actually used in each `default`, and record the exact string you ran as
  `verification.rendered_command`. Rendering the defaults must reproduce it byte for byte — the
  harness checks, and a mismatch is rejected, because otherwise `verified: true` would attest to a
  command nobody ran. Omit `params` and the command runs verbatim.

Omit `invocations` entirely for a server, or a CLI with one real mode.

**SELF-CONTAINED — the recorded command is replayed in a DIFFERENT environment from yours.** A bare
`tracelens` resolves for you only because of your shell's `PATH` or an activated venv. Nothing that
replays this file inherits either: the editor's Run button, the probe pass and every fix episode
execute each `command` string verbatim through `bash -lc` in a fresh non-interactive shell. A command
that works here and nowhere else fails with `exit 127 command not found`, and **no later agent can
repair it** — this file lives outside the repo, so a fix episode's diff can never touch it. So:

- prepend the service venv's script dir to `PATH` **inline** in the command itself, so
  `opentelemetry-instrument` resolves (an absolute path to `tracelens` alone is NOT enough — it fails
  differently, see the compose step above);
- invoke tracelens through that same dir (`{_tracelens_cmd} run …`), never a bare `tracelens`;
- name the interpreter explicitly (`{_venv_python} -m …`), never a bare `python` — and on **Windows
  write `python.exe`**, since that is the only interpreter file that exists in `Scripts/` (there is no
  extensionless `python` beside it);
- confirm `tracelens` is **importable by that interpreter** (`{_venv_python} -c "import tracelens"`) —
  the child hook is injected via `sitecustomize` and swallows a failed import silently, leaving a
  trace file with parent-process spans only and no error;
- substitute the real path for `{_venv_bin}` (`bin/` on macOS/Linux, `Scripts/` on Windows), written
  the way `bash` reads it — on Windows `/c/Users/…/.venv/Scripts`, not `C:\Users\…\.venv\Scripts`
  (the drive-letter colon would be parsed as a `PATH` separator) — and join `PATH` entries with `:`;
- **never write a single backslash in any path in this file.** `\U` / `\A` are not valid JSON escapes,
  so the file would not parse — and inside the `command` string `bash` eats backslashes as escapes, so
  `C:\Users\SERVER\.tracelens` arrives as `C:UsersSERVER.tracelens`: a relative path, meaning the trace
  silently lands where nothing reads it and the baseline comes back empty. Use forward slashes
  (`C:/Users/SERVER/…`), which are valid JSON **and** a valid Windows path.

Then prove it: run the exact string you are about to record in a **fresh shell that has not activated
anything**, and confirm the service still comes up and `trace.jsonl` still grows. If it only works in
your current shell, it is not finished.

**REPLAY CONTRACT — the recorded `{service}` command must run the server in the FOREGROUND.** The
replayer treats the spawned process's lifetime as the service's lifetime. A command that returns
immediately looks like a dead service ("exited with code 0"), orphans the real server invisibly, and
leaves it squatting the port so every later launch fails with "address already in use". So the
recorded entry must be the plain foreground form: **no** trailing `&`, `nohup`, `disown`, or `$!` PID
echo; **no** output redirection to a log file (the replayer captures stdout/stderr itself); **no**
interactive-shell toggles (`set +H` etc. — the replay shell is non-interactive). Inline env
assignments (`FOO=bar cmd …`) and `export FOO=bar; cmd …` prefixes ARE fine, as is relying on
`working_directory` instead of a `cd`. You may well have STARTED the server in your own terminal with
`> log 2>&1 &` — that is fine for your run, but what you RECORD is the same command with those
wrappers stripped. Only a dependency entry that is inherently detached (`docker compose up -d <db>`)
may return immediately.

**`added_target_packages` records the targets YOU added that the prompt did not list.** Leave it
`[]` when you used the rendered flags unchanged; put the names you added when you followed the
own-code check above (e.g. `["examples"]` for an entrypoint in a namespace directory). It is the
only signal separating "the framework derived every target correctly" from "an agent compensated by
hand" — the two produce identical commands. Adding a flag and leaving the list empty hides a gap in
the engine's target derivation and makes the next person debug a bug that was already being worked
around. Record what you added, not the full flag list.

Rules for the deliverable:

- **`commands` holds ONLY the long-running start command(s)** — the precise strings that *launch a
  process and keep it serving*. EXCLUDE every install (`pip`/`uv pip install`/`--reinstall`/the OTel
  pin block/`npm|bun|poetry install`/`uv sync`), every diagnostic (`--help`/`--version`/`which`/
  `python -c "import …"`), and every probe (`lsof`/`curl`/`wc -l`). The normal case is **exactly one**
  tracelens entry; add a SECOND entry only for a separate long-running **service dependency** you
  genuinely started (e.g. `docker compose up -d <db>`), ordered dependency-first.
- **Writing this file is MANDATORY on every exit path**, including failure. If you could not bring
  `{service}` up, set `"verified": false`, put what you observed in `verification` (port, last
  `http_status` or `null`, the failure symptom), and still record the start command you ran or
  intended — a `verified: false` file is the correct output of a failed bring-up.
- **Last check before writing: no bare `tracelens`, no bare `python`.** Re-read the `{service}`
  entry's `command`. If it starts with `tracelens ` or contains ` -- python `, it is NOT
  self-contained and will fail on replay with exit 127 — qualify both with the venv script dir and
  add the inline `PATH=` prefix before saving.
- Emit **valid JSON only** (no trailing commas, no comments, no Markdown fences in the file). Use the
  **real** values you used — the actual port, the actual `--target-package` flags, the real venv
  script dir substituted for `{_venv_bin}`, the real
  `{_caps_base}/{tracelens_subdir}{service}/trace.jsonl` output path.

After writing the file, print a short final summary: what you started, which port, and the tracelens
output path.
