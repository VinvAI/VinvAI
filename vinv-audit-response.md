# STAGE 1 — 🔴 BLOCKERS (before this touches a user's machine)

### BLOCK-1 · Undrained stdout → every exercise pass on a real repo hangs and is killed
**`extension/src/harness/exerciseRunner.ts:197`**
`cp.spawn(bin, args, {cwd, env})` defaults to `stdio:'pipe'`; only `stderr` gets a listener (`:203`). **`child.stdout` is never read.** It is the *only* spawn site in `extension/src` that doesn't — `indexing.ts:176`, `identification.ts:140`, `episodeLoop.ts:363`, `tracedRun.ts:152`, `rewardEngine.ts:124`, `binaryAgents.ts:69`, `harnessRunner.ts:729` all drain it.
**Fix:** `stdio:['ignore','pipe','pipe']` + a bounded `stdout` data handler.

> **▸ PARTLY VALID — mechanism real and reproduced; threshold wrong.** Grep confirms zero `child.stdout` references in the file, and all 7 comparison sites do drain. Replaying the **real** `demo-fastapi/.vinv/exercise/plan.json` through a byte-exact transcription of `runEngine`: 23 endpoints / 67,128 bytes → **exit 0 in 56 ms**; 46 endpoints / 134,251 bytes → **TIMED OUT → SIGKILL**; 69 endpoints → timed out. Bisected: **128 KiB passes, 132 KiB deadlocks** (libuv absorbs one 64 KiB read atop the 64 KiB kernel pipe). So the real rule is **~44+ endpoints**, not 23. Only `plan` is near the line — `run` emits a small summary dict, `profile` ~19 KB, `scorecard` ~8.7 KB.
> **Root cause / design decision:** `_emit` (`cli.py:52-53`) prints the *entire* returned dict with `indent=2`, and `build_plan` returns `"endpoints": plans` (`plan.py:418`) — the full per-endpoint plan, identical to what it just wrote to `plan.json`. The extension only ever needed the exit code, so `runEngine` was written as an exit-code-only helper and stdout was left unattached. This was a reasonable local decision that became a latent deadlock once the payload grew; it grows monotonically with agent activity, since `plan.py:406-407` folds authored `semantic_inputs` back into each record.
> **Side effect / limitation:** deterministic once crossed, silent for 180 s per occurrence, and the stage retries. The message points at the engine, not the pipe, so it reads as "the exerciser is broken on big repos."
> **Why missed:** the module header says it outright (`:19-20`: *"Pure parsing helpers are exported for the pipeline-wiring unit tests (which never spawn a process)"*). `runEngine` has **zero test coverage**, and the one repo the team demos on sits just under the threshold.

### BLOCK-2 · `child.kill()` instead of the codebase's own `killProcessTree` → orphaned processes
**`exerciseRunner.ts:206`**
`proc.ts:80-114` exists **specifically** because Windows `child.kill()` doesn't kill the tree. Not used here.
**Fix:** use `killProcessTree`; add `detached:true` + `process.kill(-pid)` on POSIX.

> **▸ VALIDATED** — negligible on POSIX today, real on Windows. `proc.ts:86` exports `killProcessTree`, `:76` exports `hiddenBackgroundOptions`, and every other engine spawn uses one or both (`serviceRunner.ts:170/243`, `goalSuggest.ts:151/167`, `rewardEngine.ts:95/129`, `binaryAgents.ts:61/73`, `episodeLoop.ts:348/482`, `harnessRunner.ts:462/465, 888/943, 1054/1064, 1449/1460`). `exerciseRunner.ts` **imports nothing from `../proc`**.
> **Root cause:** `runEngine` was written as a fresh minimal helper rather than derived from the existing engine-spawn idiom, so it inherited none of the platform conventions the helper exists to centralise. Same root cause as OPS-16.
> **Side effect / limitation:** POSIX impact is genuinely near-zero — the four invoked subcommands are pure-Python with no subprocess use. On Windows the resolved binary is a uv trampoline (`.venv/Scripts/exerciser.exe`) that `CreateProcess`es `python.exe`; `child.kill()` kills the launcher and orphans the Python child, which keeps issuing HTTP probes and planting state-ledger rows with no owner. Note a naive fix is dangerous: without `detached` on POSIX the child is not in its own group, so `process.kill(-pid)` would signal the **extension host's** group.
> **Why missed:** POSIX-only development; the failure needs Windows *and* a timeout to co-occur. No test spawns the engine.

### BLOCK-3 · `profile`/`scorecard` failures discarded → failure reported as success
**`exerciseRunner.ts:302-313`**
Both `runEngine` return values are thrown away (`plan`/`run` correctly check `step.ok`).
**Fix:** check `step.ok` for both; return `outcome:'failed'` with the error.

> **▸ VALIDATED — and the register understated it.** Executed: missing `profile.json` → `null` → `{"phase":"done","endpointsCovered":0,"total":0,...}` → Auto-Pilot prints *"Exercised 0/0 endpoints — 0 invariant(s), no issues"*. **The stale case is worse and more common**: `profile.json` from a prior pass survives a crashed step, so the pass reports last week's `16/23 endpoints, 8 invariants` as *this* pass's result and `autoPilot.ts:383` prints it as success.
> **Root cause / design decision:** a deliberate *"artifacts are the source of truth, the engine is advisory"* design — codified by `exerciseWiring.test.ts:91` (*"missing artifacts degrade to zeros, never throw"*) — applied to the two steps whose **only job is to produce those artifacts**. The invariant is correct for `primeExerciseState` on cold activation and wrong mid-pass; the same helper serves both callers.
> **Side effect / limitation:** `outcome:'done'` marks the ledger stage **terminal** (`autoPilotMachine.ts:337`), so the stage never retries. It survives across sessions via `primeExerciseState`.
> **Why missed:** the failure *is* the tested behaviour. A reviewer reading the tests sees the coalescing as intentional — because for one of its two callers it is.

### BLOCK-4 · No cancellation, no teardown on deactivate
**`exerciseRunner.ts:226`, `extension.ts:236-239`**
**Fix:** thread a `CancellationToken`; register the child handle for disposal in `deactivate()`.

> **▸ PARTLY VALID** — every anchor is factual, but the framing as exerciseRunner-specific is not. `runInsightPass` (`insightRunner.ts:243-246`) and `runProbePass` (`probeRunner.ts:760-764`) are **identically token-less**. All three post-green stages share the gap; a token *is* in scope at `autoPilot.ts:316` and used at `:336, :443, :472, :517`.
> **Root cause:** the three post-green stages were built from one template that predates the token plumbing added for the service/bring-up stages. Cancellation was threaded through the *service* half of `drive` and never extended past the `anyGreen` boundary.
> **Side effect:** Stop during exercise leaves up to 4 × 180 s = 12 min of engine children hammering a live service and planting `state_ledger` rows. Closing the window is worse — `deactivate()` doesn't touch them, and since `:197` has no `detached` they may outlive the extension host.
> **Why missed:** cancellation looks well-plumbed if you read `drive`'s first 300 lines; the drop-off is at a *stage boundary*, not at a call site.

### BLOCK-5 · Unguarded `spawn` wedges the harness lock for the whole session
**`harnessRunner.ts:1051-1058`**
**Fix:** wrap in try/catch and reset `running` in the catch.

> **▸ PARTLY VALID — asymmetry real, no reachable trigger.** Confirmed: `running=true` at `:1051`, reset **only** in `settle()` at `:1274`, while the two siblings use `try/finally` (`:997-1002`, `:1383/:1537-1539`) and `:886-896` wraps the identical spawn in try/catch. But enumerating node's actual sync-throw conditions: NUL bytes in `commandLine`/`env`/`cwd` and a non-string `cwd` throw synchronously; **nonexistent cwd and EMFILE are asynchronous** (`'error'` → `:1277` → `settle` → `running=false`). `commandLine` is `"${exe}" ${harness.args}` where args is a hardcoded constant and exe a resolved path; `openTrajectoryLog` is fully try/caught. **No reachable trigger could be constructed.**
> **Root cause:** `running`'s lifetime is coupled to `settle`'s reachability rather than to the function's scope — correct-by-luck, not correct-by-construction.
> **Verdict:** worth a one-line `try/finally` for robustness; **not a live bug** and should not be a blocker.
> **Why missed:** an invariant asymmetry with no reachable trigger is exactly what static review catches and dynamic testing cannot — the register was right to look, and right that the shape is wrong.

### BLOCK-6 · Unbounded output accumulation → extension-host OOM
**`harnessRunner.ts:1243`**
**Fix:** cap with the same `.slice(-400_000)` idiom.

> **▸ VALIDATED — and the register understated why this is the worst of the group.** Both stdout *and* stderr feed one uncapped `out += chunk` (`:1238-1263`). Every peer caps: `:931` `.slice(-400_000)`, `binaryAgents.ts:69`, `episodeLoop.ts:373`, `rewardEngine.ts:121` `.slice(-20_000)` (*"Bounded ring — test output is evidence, not a transcript"*), `tracedRun.ts:151` `.slice(-8000)`. **Critically this is the longest-lived spawn and the only one with no wall-clock timeout** — `:1170` is a *silence* watchdog (adaptive 120 s floor / 900 s ceiling) that a continuously-chatty agent never trips, while `dispatchAgentPrompt` has a hard `agentDispatchTimeoutMs()`.

Scales with episode length, so it hits exactly the long autonomous sessions the product exists for.
> **Why missed:** the file contains four correct bounded ring buffers; a reviewer scanning for the pattern sees it applied and moves on.

### SEC-1 · Bearer tokens and PII written into the user's repo
**`run.py:837`, `state.py:79`, `store.py:118`**
**Fix:** redact bodies before persistence; restrict harvesting to id-shaped fields.

> **▸ VALIDATED — and broader than filed.** No redaction exists anywhere (`grep -rn "redact|scrub|sanitiz|SENSITIVE|secret"` over `src/exerciser/*.py` returns only unrelated `functions.py` hits). End-to-end run against a fake service returning a real-shaped JWT: `results.jsonl` **contains the JWT**, `state_ledger.jsonl` **contains the JWT** (rows 0 and 2 `.body.access_token`, row 4 `.input.path_params.user_id`). **The plaintext password leaks too** — the register did not name this: `planted=['admin@example.com','changethis']`.
> **Root cause / design decision:** `_execution_row` persists the whole parsed body unconditionally for any `dict|list`, and `scalar_values` harvests every string ≥4 chars with **no key-name or entropy filter** — deliberately generic, per `state.py:12` (*"no key names baked in"*). That genericity is the right call for a repo-agnostic harvester and is exactly what makes it unsafe here: the login endpoint is just another endpoint, and nothing distinguishes a credential-minting response.
